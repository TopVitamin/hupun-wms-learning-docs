# 万里牛WMS拆解与产品设计参考

这是一套面向WMS学习、产品分析和字段建模的工程化资料型项目。项目围绕万里牛电商云仓WMS（涵盖PC管理控制台、专题特性与PDA安卓端作业），把314篇原始帮助手册与业务资料拆成业务事实重构、业务流程图、产品设计抽象、字段设计参考和全域走查地图五个互相联动的层次。

项目名称沿用原始资料中的产品名称，但本仓库不是万里牛官方文档，也不代表万里牛产品的完整实现或当前版本行为。

## 这个项目解决什么问题

只看电商WMS帮助文档，容易被分散在数百个操作单页中的菜单、按钮和配置参数所淹没；直接阅读或设计字段表，又很难知道字段在哪个作业环节产生、被谁读取校验以及如何驱动库存与任务变动。本项目将原始业务资料与专业产品设计思考接在一起，帮助读者沿着下面这条路径理解WMS：

```text
原始资料归档 → 业务事实重构 → 核心作业流程 → 产品设计抽象 → 业务字段参考 → 设计验收
```

项目重点关注商品中心与库存属性、仓内策略、采购与销退预约入库、B2C单品与多品拣选出库、B2B大宗装箱称重、仓内加工形态转换、库位移动与主动被动补货、动态盲盘与库存台账、多平台电子面单、3PL计费与货主结算，以及仓内作业体验与异常反馈全链路。

## 适用于谁

| 读者 | 可以用它做什么 |
| --- | --- |
| WMS/仓储产品经理 | 学习电商云仓业务对象、单据链、策略配置与库存变化，辅助需求分析与产品设计 |
| 供应链与电商ERP产品经理 | 了解WMS与ERP、OMS、TMS、PDA、开放平台及自动化设备之间的职责边界 |
| 实施顾问、业务顾问和仓库运营人员 | 按业务链回看页面规则、作业动作和异常处理，整理培训与调研方案 |
| 数据产品经理与数据建模人员 | 从业务事实与设计模型反查实体关系、单据状态、数量计算口径与流水追溯 |
| AI课程学习者与知识库建设者 | 学习如何将海量碎片化帮助手册、专题功能和手持端文档重构为高密度业务知识库 |

如果你需要的是可以直接部署的WMS代码、官方API文档、数据库建表脚本或某个客户项目的定制实施方案，这个仓库不能直接替代它们。

## 快速开始

### 推荐阅读顺序

1. 先看本README与[00-全面走查与学习地图](./00-全面走查与学习地图.md)，了解全貌、资料职责和事实边界。
2. 打开[02-跨章节主链与学习导航](./02-按章节拆分的流程图/00-跨章节主链与学习导航.md)，建立订单履约、现场任务、库存变动与包裹交接的全局主链模型。
3. 打开[01-按章节拆分的md文件](./01-按章节拆分的md文件/README.md)，按12个主线章节确认万里牛原文记录的业务事实、页面规则与配置项。
4. 打开[02-按章节拆分的流程图](./02-按章节拆分的流程图/README.md)，观察端到端作业流向、前置条件判断与异常分支走向。
5. 打开[03-WMS产品设计精华知识借鉴](./03-WMS产品设计精华知识借鉴/README.md)，理解通用对象关系、状态机、数量守恒、异常处理和产品设计取舍。
6. 打开[04-WMS的字段设计参考借鉴](./04-WMS的字段设计参考借鉴/README.md)，核对单据与库存实体的字段模型、来源校验与下游影响。
7. 结合[20-原始字段观察与设计验收](./04-WMS的字段设计参考借鉴/20-原始字段观察与设计验收.md)，按输入、系统处理、页面反馈、数据结果与异常回退进行闭环验收。

## 这个项目是怎么做出来的

1. 确定事实边界：以原始语雀操作手册、专题功能和PDA手持终端文档作为唯一事实源，严格规定未说明内容不得主观臆造。
2. 归集与重构事实：将分散在不同分类目录的314篇正文源文件按业务主线重组为12个主线大章节，保留小节对应的源文档路径与图文引用。
3. 绘制Mermaid流程图：按章节提炼40张流程图，梳理前置条件、判断分支、异常回流与系统结果，并补充跨章节端到端主链。
4. 提炼通用产品设计：脱离具体SaaS页面的菜单表象，抽象出业务单据、执行任务、库存实体与流水记录，并针对加工、3PL费用和现场作业体验补充独立模块。
5. 构建字段参考模型：梳理核心单据与库存实体的表头与明细字段，标明字段来源、校验时点、枚举基线与下游影响。
6. 打通字段与验收闭环：补充20号设计验收文档，将原文观察词、建议设计字段、下游消费与业务验收问题串接成闭环。
7. 建立全域学习地图：输出00号全面走查与学习地图，梳理四级问题清单，为不同角色提供可落地的学习与实践路径。
8. 静态验收与质量校验：通过脚本核验12章全覆盖、40张Mermaid流程图语法闭合、跨文件相对链接与引用锚点。
9. 纳管版本控制：初始化仓库分支，保护原始资料合规性，通过规范化提交记录每次工程迭代。

## 事实、建议和风险怎么区分

在`03`和`04`中，通过规范化标记区分内容性质：

> **[参考事实]**：万里牛手册明确写出或展示的页面、动作、参数或结果。
>
> **[归纳判断]**：从多个章节或操作环节整理出的对象关系或设计规律。
>
> **[建议设计]**：面向通用型WMS提出的产品、数据和流程方案，不代表万里牛已有此实现。
>
> **[待确认]**：手册或当前资料不足以支持确定结论，需要在业务调研或研发对接中确认的内容。

万里牛当前原始资料以操作文档和功能专题为主，未包含底层数据库数据字典。`04`层的字段编码、类型与约束属于逻辑模型与建议参考，使用前需结合实际系统环境确认。

## 发布到GitHub前的注意事项

1. 先确认原始资料的公开权限：`00-源文件/`包含本地回查用的原始操作文档与附件。若涉及商业保密或版权限制，应通过`.gitignore`排除，不要强行提交到公开仓库。
2. 本项目不是官方规格：不要依据这里的建议字段名、推导模型直接生成生产环境数据库建表脚本或对外接口契约。
3. 字段为建议逻辑模型：当前资料以业务事实为主，字段设计属于逻辑参考，不代表万里牛实际底层物理表结构。
4. 图示需要回到来源：流程图是对手册事实的可视化整理，遇到业务冲突时以`01`正文和`00`源文件为准。
5. Mermaid渲染环境差异：本项目已做静态语法检查，建议在GitHub或支持Mermaid的Markdown渲染器中查看。
6. 开源许可证与素材合规：公开仓库不代表自动获得原始截图或商标的授权，准备公开时需注意合规并补充适宜的许可证。
